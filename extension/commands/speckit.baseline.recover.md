# Recover project memory

Consider `$ARGUMENTS`. Existing code shows observed behavior; it does not establish
approved intent. This command only proposes; the `speckit-baseline-amend` command applies approved
rows. It also handles code changed outside the process when memory already exists.

Memory is committed and often public. Never write absolute or home paths, usernames,
hostnames, IP addresses, internal URLs, emails, ports of private services, credentials,
tokens, keys or secrets, or any value copied from `.env` / config files. Describe
things generically (`the config file`, `the database host`); repo-relative paths are fine.
Apply this to source tags, evidence and questions too. Run the blocking privacy check
before saving any memory for commit; rewrite a hit generically or drop the row.

1. Read constitution and any existing product, architecture and decisions files.
   Run `python3 .specify/extensions/baseline/scripts/baseline_check.py --mode advisory`.
   Report every missing/malformed file and citation; do not silently load partial
   context. Advisory changes no files or settings and cannot approve intent or DONE.
2. Inventory code, tests and docs, including root entry points, manifests, lockfiles,
   relevant hidden CI/deployment paths and contracts. Account for each relevant area
   as a part or explain its exclusion. Evidence paths accompany every proposed row.
3. With no baseline, propose a first baseline from the memory templates. Separate
   **observed behavior** from **approved intent** visibly in the proposal. Draft
   capabilities as proposed, stack and parts from evidence, and Spirit purpose/users,
   PR promises and non-goals for the user to decide. All 14 Delivery areas remain;
   observations suggest rules, never prove non-negotiables. Unresolved areas are
   undecided, and n/a needs a reason. Planned paths need no code yet.
4. With an existing baseline, compare relevant observations against approved rows,
   boundaries, Delivery standards and decisions, including rejected options and why.
   List code changed outside the process, conflicts and uncovered areas with evidence.
   Propose amendments tagged new, merges with or contradicts existing rows. Offer
   fixing code to match intent as an alternative; do not normalize drift automatically.
5. Record only rationale supported by docs, comments or history. Do not invent reasons
   from implementation choices. Unknown intent becomes an open question. Evidence of
   behavior is not evidence that the user chose it.
6. Present the proposal with evidence, uncertainty and exclusions. Send it to amend
   for row-by-row approval, preserving rejected options and answers. Do not edit
   accepted memory yourself. After approved amendments run the blocking memory check;
   report remaining questions and structural errors without declaring the code correct.
